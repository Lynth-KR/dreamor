# Testing

For people working on dreamor; `AGENTS.md` says when to read it.

What each configuration runs (the commands are `AGENTS.md`'s, "Build and test"):

- **Stub mode** (no solver's directory) runs every test in `tests/unit/` (one part each), `tests/stress/`,
  `tests/examples/` (the example's model against the same model written by hand with `std::map`s and loops, the one
  test that would see a mistake every backend shares) and `tests/docs/` (the code of the docs as written there) against
  the Concert stub, checks every case in
  `tests/compile_fail/`, runs every case in `tests/contract_fail/` (not under `-DNDEBUG` or ThreadSanitizer: below), and
  syntax-checks `tests/cplex/*.cpp` and the Concert example.
  - `compile_fail/set_too_many_columns.cpp` pins the 65th column's message. It is generated by
    `tools/gen_arity_tests.py` - edit the script and re-run it, never the file; `--check`, which CI runs, fails on a file
    that is not the script's.
  - `stress/test_differential*.cpp` (nine, one per row layout: `std::size_t` columns, 4- and 8-byte columns in turn,
    `Ref` columns, a `std::string_view` column, `std::uint32_t` columns, owned `std::string` columns, enums, a user
    type whose hash collides, integers of mixed sign and width), a stress test, check the set layer, its tables
    (`ParamTable`, `SolutionTable`) and sumExpr against a plain-STL reference (`tests/stress/differential.hpp`) over a
    few hundred random cases from a fixed seed. `DREAMOR_DIFF_SEED` and `DREAMOR_DIFF_CASES` replace the seed and the
    number of cases; `DREAMOR_DIFF_LARGE=1` adds a large case after every twenty, sets of tens of thousands of rows,
    which a release build sets (below); in a debug build it takes a run from half a second to forty. A change to the
    semantics of rows (order, repeats, grouping, neighbours) has to change the reference too.
  - `stress/test_allocation_failure.cpp` makes each allocation of a model's set work fail in turn, the first to the
    last, and checks that what survives the `std::bad_alloc` holds what the reference's exception guarantees say.
  - `stress/test_row_hints.cpp` checks a lookup by columns against hints that point anywhere: one at every byte of the
    rows and just outside them, in each of the four slots and as the row sumExpr published, over keys of 4 to 80
    bytes; sets made and destroyed so that the hints they left lie in later sets' rows; lookups on eight threads before
    the hash is built. Each lookup must give what the row's address gives.
  - `stress/test_shapes.cpp` checks the set engine's situations, each over a shape written for it, as a chain and in
    set-builder notation, against nested loops over random data; each shape pins its visit order with a
    `static_assert`.
  - Why these differential tests and why they are enough - the branches they reach, the large cases, what is
    deliberately not run - is `differential-test.md`, with what to check again after a change.
  - `unit/test_determinism.cpp` holds the same result, byte for byte, on every platform and every run: one instance
    drawn by a generator of its own (`tests/support/determinism.hpp`; std's distributions draw differently by standard
    library) through the set layer and the example's model on the stub, printed and held against
    `unit/determinism.txt`, three times, the heap shaken from a seed before each. Its keys hash differently by platform
    and run (text by `std::hash`, a `Ref` by its address), so an order that leaked a hash or an address fails it, on
    the jobs of every platform alike. `highs/test_determinism.cpp` does the same for the model HiGHS receives
    (`highs/determinism.txt`), unsolved. A change to an order is meant to show there: rewrite the file with
    `DREAMOR_DETERMINISM_WRITE=1` and read its diff; a mismatch prints the first line that differs and writes the
    whole text beside the build's tests.
- **`DREAMOR_ORTOOLS_DIR`** runs `tests/mathopt/*.cpp`, the MathOpt example, the ported samples in
  `examples/mathopt_samples/`, and `tests/mathopt/compile_fail/`.
  `test_cross_backend.cpp` builds the example on both backends and compares the constraints.
- **`DREAMOR_HIGHS_DIR`** runs `tests/highs/*.cpp` (solving with HiGHS), the README's program as `tests/docs/readme.py` takes it out of `README.md` (the lines it prints are the README's), `tests/docs/highs/` (the guide's code that solves: its model, `tests/docs/guide/model.hpp`, solved whole), the HiGHS example, `tests/highs/compile_fail/` and, in a debug build, `tests/highs/contract_fail/`.
  `test_cross_backend.cpp` there builds the example on Concert (the stub) and HiGHS and compares the constraints;
  `test_cross_backend_random.cpp` builds random models (`tests/support/cross_backend.hpp`) on both, and on MathOpt in
  `tests/mathopt/`, and compares them exactly. HiGHS drops a coefficient at most `small_matrix_value` (1e-9) from a
  row, which the other backends keep; the comparison leaves those out on the HiGHS side.
- **`DREAMOR_CPLEX_DIR`** solves with real CPLEX. CPLEX is not on CI, so run it locally when you touch Concert-facing code
  and have CPLEX available.
- **Warnings** are what dreamor's own code is held to; the CMake target adds none, so users keep their own flags.
  The library and its tests build with `strict` in `tests/CMakeLists.txt` (`-Wconversion`, `-Wsign-conversion`,
  `-Wold-style-cast`, `-Wfloat-equal`, ... and `-Werror`; with cl.exe and clang-cl, `/W4 /WX`): a header that warns
  there would warn in a user's strict build. The code users read - the docs' code (the README's program, the guide's under
  `tests/docs/guide/` and `tests/docs/highs/`) and
  `examples/` - builds with `user`, `-Wall -Wextra -Werror`, as a user builds it, and `-Wfloat-equal`, so that the
  docs' checks keep the rule below; a library test that includes
  `examples/` takes it as a system header. The ported samples and the compile_fail cases build with `-Wall -Wextra`
  only - a warning must not become a compile_fail case's first error.
- **Doubles are compared with care.** A value computed two ways seldom agrees to the last bit, so a computed value
  is compared within a tolerance (`near` in a test that solves). A value that comes back exactly as it went in - a
  bound, a datum, a stub's solution - is compared with `exactlyEqual` or `isExactlyZero` from
  `tests/support/float_compare.hpp`, never with `==`: the name says the exact comparison is meant, `-Wfloat-equal` rejects a
  bare `==`, and a change to how exact values are compared is made in one place. `exactlyEqual` is `==`, not a
  comparison of bytes: `0.0` equals `-0.0`, and a NaN equals nothing.

## Where a configuration departs

A configuration runs every test of the kinds it builds, each the same way, except in the cases below. Each is
decided in `tests/CMakeLists.txt`, where a comment gives the same reason; a new exception is added there and here.

- **A release build** runs the differential tests' large cases too (`DREAMOR_DIFF_LARGE=1`). Sets of tens of
  thousands of rows pass the 16384 entries from which an index tags its slots, and go through the release build's own
  way of indexing a table's rows. A debug build leaves them out, because they take a run from a second to a minute.
- **AddressSanitizer** runs the stress tests a second time with its quarantine off. ASan holds freed memory back, so
  no set is made where a destroyed one was, and a hint that a destroyed set left never lies inside a set made after
  it; with memory handed back at once, it can.
- **`-DNDEBUG`** leaves out `tests/contract_fail/` and `tests/highs/contract_fail/`, because the checks that the cases
  break are compiled out.
- **ThreadSanitizer** leaves out the contract_fail cases, because a program that stops on purpose gives it nothing to
  find. It also leaves out `stress/test_allocation_failure`: ThreadSanitizer's interceptor of `pthread_once`, which
  libstdc++'s `std::call_once` calls, leaves the flag marked as running when the callable throws, so the next call
  waits forever (GCC 13 and Clang 18 alike; libc++'s `std::call_once` does not go through it). The test makes the
  first build of a set's lookup index throw and then looks the set up again, which the standard allows, so it would
  hang; it starts no thread, and the AddressSanitizer presets run it. Every test runs under `setarch -R`, with address
  randomization off: GCC 13's ThreadSanitizer stops before `main` when the kernel randomizes addresses more widely
  than its fixed shadow layout allows, as Ubuntu's kernels have since 2024. Newer runtimes, Clang 18's among them, run
  the program again without randomization themselves.

## Coverage

CI's coverage job measures how much of `include/dreamor/` the tests run, and Codecov shows the figure. The `coverage`
preset builds stub mode and the MathOpt and HiGHS backends, on the OR-Tools prebuilt, with Clang 18's source-based
coverage, and runs the unit, stress, docs, examples and contract_fail tests; a contract_fail case aborts on purpose,
and the counters are written as the program runs, so it counts. `tools/coverage/lcov.py` then writes an lcov file for each
test program, and Codecov adds them up line by line. Locally: `ORTOOLS_DIR=<prebuilt> cmake --workflow --preset
coverage`, then `python3 tools/coverage/lcov.py build/coverage --summary`. `--html` adds a report to read in
`build/coverage/html/`, each template instance apart and the branches counted; its totals can fall short of the lcov
files', since one report over every program drops some records (`lcov.py`).

What the figure leaves out, and why:

- **Functions that no test instantiates.** A template that no program instantiates generates no code, so it is in
  neither the numerator nor the denominator, and the figure says nothing of it. `uv run
  tools/coverage/uninstantiated.py build/coverage`, after `lcov.py`, lists them through libclang: the `consteval`
  checks and the overloads that only stop a misuse with a `static_assert`, which the compile_fail cases check, are
  expected; any other is a function that a program could call and no test does.
- **Code that runs only at compile time.** A line that the compiler evaluates - a `constexpr` function in a constant
  expression, a `static constexpr` member's initializer - runs in no program. `plan.hpp`, the visit-order planner,
  runs at compile time whole, so `.github/codecov.yml` leaves it out. In other headers such lines stay, and count as
  not run: the `static constexpr` arrays that immediately invoked lambdas build in `set.hpp` and `key_args.hpp`, and
  `writeVisitOrder`, the text of `visitOrder()`. Leaving their files out would hide the code that does run. They are
  checked where they are evaluated, by `static_assert` and by every set that is built.
- **What no correct run reaches.** `unreachable()` in `unreachable.hpp` is where a release build goes on a broken
  contract; `.github/codecov.yml` leaves it out.
- **compile_fail and the syntax checks** compile and run nothing, so they add no line: what they cover is what the
  compiler rejects.
- **The release build's own paths.** The preset is a debug build (`-O1 -g`), so it runs the debug checks and
  contract_fail, and not what a release build alone runs, such as `FlatSlots::placeDistinct`, by which the release
  build's row index places its rows; the release presets run those, uncounted.
- **Real CPLEX**, which is not on CI: Concert is counted against the stub.

## Concert stub

`tests/stub/` stands in for the Concert headers so CI runs without CPLEX. It mirrors the real header layout. For
example, `IloModel` has its own header, as in real Concert, so a missing include fails here as it would against
CPLEX. If library code starts using another Concert API, add it to the stub the way the real headers declare it.
Confirm with the `cplex` preset when possible.

`compile_commands.json` (from `python3 tools/gen_compile_commands.py`) is machine-specific; do not commit it.
